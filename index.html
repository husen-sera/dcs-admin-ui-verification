DCS admin re-skin · functional verification

The new admin UI does not break existing functionality

Staging (current, stock Django admin) and ui-improvement (new UI, django-unfold) were compared on identical data — screen by screen, list by list, form by form, filter by filter, including a real save and the GraphQL API. Three differences turned up; every one is either an intended change or an artefact of the review environment. Nothing was lost.

01The two environments

Both run on the same server and the same PostgreSQL cluster, and the new UI's database is a clone of the staging one. So the same rows should come back in the same order — and where they don't, that difference is the implementation, not the data. That is what makes this comparison meaningful.

What was checked individually

  • Both environments register exactly the same 17 admin models Nothing became unreachable or appeared out of nowhere.
  • List contents match row by row — 15 of 17 match on ordering too Compared by primary key rather than by count, which would also catch a filter quietly dropping rows.
  • Save, Save and continue editing, and Save and add another all exist on both The new theme renders them as <button> and stock Django as <input>, but the submit names are identical.
  • A real save was performed in a browser and read back from the database Email, permission group and every flag survived the round trip. A hand-built POST would have missed the theme's JavaScript widgets, so this was done with an actual click.
  • Bulk actions work In the new UI the action bar appears once a row is selected, rather than sitting above the table.
  • Filtering, sorting, pagination and search return the same rows Filters moved from a right-hand sidebar into a Filters button — where they live changed, what they do did not.
  • Activity-log date filtering, the summary page and CSV export all work on both Both return text/csv; charset=utf-8.
  • The GraphQL API is untouched The UI branch's schema is byte-identical to the commit it branched from, so the frontend needs no work.
  • All six migrations are metadata-only, with no numbering collision against dev They rename labels. No table structure and no data changes.
  • The emergency kill switch was exercised on the live server With ADMIN_UNFOLD_ENABLED=False every page still served, the theme disappeared, and the Japanese labels stayed.

03The three differences

None of these is something that broke. Here is what each one is and why it is there.

IntendedThe user list now sorts by email instead of username

The same 36 users appear in both environments — only the order differs. People sign in with their email address, while the username column holds generated values such as Dy-hayashiKy-hayashiHy-hayashi4y-hayashiV, which made the list hard to scan. The new UI sorts by email on purpose (app/user/admin.py).

Review envBackground-task history does not line up

Staging runs a live worker that keeps writing new task records, while the cloned database stopped at the moment it was copied. This is data freshness, not an implementation difference. The other 16 models matched exactly.

Action needed — phase 5ui-improvement is 8 commits behind dev

Those commits include a security fix that closed unauthenticated endpoints, and they removed the GraphQL root field projectDistributionRecipientMappingList on dev. The UI branch still carries it. This is not caused by the UI work — rebasing onto dev, which is the first step of phase 5, resolves it. The six new migrations do not collide with anything on dev.

None of them changes a model, a migration or the GraphQL schema, so none of them changes what was verified above.

The six slices

  • Charts, and a bar denominator that was wrong The time-of-day bars were scaled to the period total, so the busiest hour filled 11% of its track. They are scaled to the peak now, and the report has a daily trend line and an hourly chart. Each chart carries a data table, because a canvas does not answer browser zoom.
  • The 集計 report rebuilt It was 13,627px of eight tables, 60% of it one list of unused features. Now: a summary row, charts, rankings, and the long lists behind disclosures.
  • The admin home page It rendered unfold's full app list — nine sections, 2,005px, re-listing what the sidebar already shows, on the page every session lands on. Replaced by activity figures, a short row of shortcuts, and the full list behind one click so nothing became unreachable.
  • A dark-mode toggle a keyboard can reach The theme ships one, as <a> elements with no href — not in the tab order, no response to Enter, 18px tall, and marking the active choice by colour alone. Its only content was an icon ligature, so a screen reader read the string dark_mode. It is now real buttons, 24×24, named in Japanese with the current theme in the name, and closable with Escape.
  • The home page drew 3,318 events and named 2,263 of them The activity chart plots every event; the cards above it showed four of the five types. On the review data that is 4,396 of 4,949 events — 89% of all activity — drawn and never named. The row is now built from the report's own card list, so the two screens cannot drift, and the page states the total so the breakdown can be added up.
  • The report says what IS used, not only what is not A list of every function with its usage, which ones were used for the first time in the period, and the record counts the dashboard shows. On the review data: 210 functions, 55 used, 16 used for the first time, 155 unused.

Two things worth saying plainly

  • "New" means first used in this period, not newly shipped The list of functions comes from the GraphQL schema, which carries no ship date — so "when did this arrive" is not a question the data can answer. When a feature was first used is, and for one nobody could use before it existed the two are the same.
  • The emergency kill switch still works, and still matters Everything above is markup and queries. ADMIN_UNFOLD_ENABLED=False plus a restart removes the theme and leaves the Japanese labels, the activity log and the CSV export working, exactly as photographed in section 05.

08What happens next (phase 5)

To be done once the design is approved. This verification was about confirming the preconditions are in place.

  1. Rebase ui-improvement onto dev — picks up the 8 commits, including the security fix.
  2. Merge into dev — the six migrations are metadata-only and collision-free, already confirmed.
  3. Check staging by hand — re-walk the screens in this report on the merged staging build.
  4. dev → main (production release) — start.sh reports success even when a step fails, so verify the release independently, including migrate --check.
  5. Check production by hand — if anything looks wrong, ADMIN_UNFOLD_ENABLED=False restores the old admin immediately.

No frontend work is required. The GraphQL schema is unchanged and the SPA never touches /admin/.
