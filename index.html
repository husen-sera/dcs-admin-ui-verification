個別に確認した項目

  • 登録モデルは両環境とも 17件で完全一致 管理画面から操作できる対象が増減していないこと。
  • 一覧の中身が ID 単位で一致（17件中 15件は並び順まで同一） 件数ではなく各行の ID を突き合わせ。絞り込み条件の取りこぼしを検出できます。
  • 保存ボタン（保存／保存して編集を続ける／保存してもう 1つ追加）が両環境に存在 新 UI は <button>、標準は <input> で出力されますが、送信名は同一です。
  • 実ブラウザで実際に保存し、DB に反映されることを確認 メールアドレス・権限グループ・各フラグが保存後も保持されていました。
  • 一括操作（チェックボックス選択→操作実行）が動作 新 UI では行を選択したときに操作バーが現れます。
  • 絞り込み・並び替え・ページ送り・検索が同じ結果を返す 新 UI は絞り込みが右側サイドバーから「絞り込み」ボタン内に移動していますが、効き方は同じです。
  • ユーザー活動ログの期間絞り込み・集計・CSV 出力が両環境で動作 CSV は両環境とも text/csv; charset=utf-8 で返却。
  • GraphQL API は無変更 UI ブランチの SDL は分岐元とバイト単位で同一。フロントエンド側の対応は不要です。
  • マイグレーション 6件はすべてメタデータのみ・dev と番号衝突なし ラベル定義の変更だけで、テーブル構造もデータも変わりません。
  • 緊急停止スイッチが実機で有効 ADMIN_UNFOLD_ENABLED=False で標準画面に即復帰。日本語ラベルは残ります。

03見つかった 3件の差分

いずれも「壊れている」ものではありません。内容と理由を明記します。

意図した変更ユーザー一覧の並び順がユーザー名順 → メールアドレス順

表示される 36件は両環境でまったく同じで、順番だけが違います。 ログイン ID はメールアドレスであり、ユーザー名側には Dy-hayashiKy-hayashiHy-hayashi4y-hayashiV のような 自動生成値が入っているため、実運用では探しにくくなっていました。 新 UI では app/user/admin.py で明示的にメールアドレス順に変更しています。

検証環境の都合バックグラウンド処理の履歴が一致しない

staging は常時ワーカーが動いていて新しい実行履歴が増え続けますが、 新 UI 側の DB は複製した時点で止まっています。実装差ではなくデータの鮮度差です。 それ以外の 16モデルはすべて一致しました。

要対応（フェーズ 5）ui-improvement が dev より 8コミット遅れている

その 8コミットにはセキュリティ修正（未認証エンドポイントの封鎖）が含まれ、 GraphQL のルートフィールド projectDistributionRecipientMappingList が dev 側で削除されています。新 UI ブランチにはまだその削除が入っていません。 UI の作業が原因ではなく、フェーズ 5 の最初の作業である 「dev へのリベース」で自動的に解消します。マイグレーションの番号衝突はありません。

07この先に必要なこと（フェーズ 5）

デザイン承認後に実施する想定の手順です。本検証はその前提条件を満たしているかの確認でした。

  1. ui-improvement を dev にリベース — 上記の 8コミット（セキュリティ修正）を取り込みます。
  2. dev へマージ — マイグレーション 6件はメタデータのみ、番号衝突なしを確認済み。
  3. staging で目視確認 — 本レポートと同じ画面を、マージ後の staging で再確認。
  4. dev → main（本番リリース） — start.sh は失敗しても緑で終わるため、リリース後に migrate --check まで含めた独立確認が必要です。
  5. 本番で目視確認 — 問題があれば ADMIN_UNFOLD_ENABLED=False で即時復旧できます。

フロントエンド側の対応は不要です。GraphQL スキーマは無変更で、 SPA は /admin/ を参照していません。
